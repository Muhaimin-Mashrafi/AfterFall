## 1. Concept and premise

Unchanged in spirit. A settlement of survivors tries to rebuild. You are the **Humanity Overseer**: you watch, inspect, decide and investigate. You do not move people. An **Observer**, a rule-based AI that looks like a helper, quietly shapes information and social conditions. The story is generated by a **Narrator** from real simulation events. At critical moments the story pauses and asks for a decision. **[NEW]** In the live demo, the room can vote on those decisions.

Central moral (kept): *"The cruelest destruction is the kind that convinces people they chose it themselves."*

## 3. The Observer (antagonist)

*(The first Observer sections are not in the PDF I received. This keeps the surviving text.)*

**Intervention strategies**

| Policy | Tier | Effect |
|---|---|---|
| `InformationDistortionPolicy` | MUST | Alters information delivered to a target group |
| `TrustErosionPolicy` | MUST | Exploits existing relationship tension |
| `ResourcePressurePolicy` | MUST | Shapes perceptions of scarcity |
| `SelectiveDisclosurePolicy` | MUST | Reveals some facts and withholds others |
| `FearAmplificationPolicy` | **[CUT] to COULD** | Overlaps with the above for the demo |

**Rule-based decision model.** Deterministic rules, not machine learning, no external LLM. The Observer reads trust, morale, resources, tension and recent decisions, and selects a policy with explicit thresholds:

```
IF settlementTrust is low
AND foodShortage is active
AND factionTension is high      // MUST tier uses "relationship tension" if factions are not built
THEN evaluate an information-distortion intervention
```

**Intervention boundary.** The Observer never mutates a `Survivor`. It proposes an `Intervention` (a Command) through the simulation command queue. The engine validates and applies it at a safe tick boundary.

**Evidence.** Every observation and intervention records tick, target, policy, reason, intended effect, actual result and status. The original report and the altered version are both kept so inconsistencies can be shown. These records become the Recovered Records the user discovers.

**Population:** start with **20 to 30 survivors** in MUST. Scale to ~100 (SHOULD) only after the determinism and shutdown tests pass at the smaller size. Population is a config value; code must not assume a number.

Carried over unchanged from the original (see original section 4 for the full tables):

- **Professions:** Farmer, Scavenger, Medic, Guard, Engineer, Builder, Teacher, General Worker. **MUST uses Farmer, Scavenger, Medic, Guard, General Worker.** The rest are SHOULD.
- **Relationships** store trust, affection, hostility, type and history. **Memories** store significant events only (event, day, emotional impact, related survivor, source event id).

**Regions [CHANGED].** The seven zones in the original are kept as *labels* for story scenes. For processing, the world is split into **four processing regions** (for example one per quadrant). In MUST, a region is a set of survivor ids plus region-local state, with no map drawn on screen.

## 5. Simulation engine and autonomous behaviour

Unchanged. The simulation runs independently of the browser. A virtual `WorldClock` requests ticks, and the tick-to-time mapping is configurable (never hard-coded). `TickCoordinator` applies queued commands, prepares the immutable `WorldView`, coordinates workers, merges results and publishes state. It does not implement survivor behaviour itself.

**Behaviour cycle:** read state, read `WorldView`, weigh personality and profession, ask the current `Behavior` (Strategy) for an `Action` (Command), generate immutable `SimEvent`s, publish, update at the tick boundary.

**[CHANGED] clarification of step 5 and 8.** A worker does not apply an action to shared state. It *evaluates* the action against the immutable `WorldView` and returns the proposed state change and events as part of its `RegionResult`. The change takes effect when the coordinator merges (section 12).

```java
public interface Behavior { Action decide(Survivor survivor, WorldView world); }
public interface Action   { List<SimEvent> apply(WorldContext context); }
```

MUST behaviours: `SeekFoodBehavior`, `WorkBehavior`, `RestBehavior`, `SeekMedicalHelpBehavior`. SHOULD: `SocializeBehavior`. COULD: `FleeBehavior` (needed once raids exist). MUST actions: `EatAction`, `WorkAction`, `RestAction`, `HealAction`, `MoveAction`. `SocializeAction` is SHOULD. `TradeAction` is COULD.

## 6. Crises, resources and the story arc

### 6.1 Crises [CHANGED: two in MUST]

| Crisis | Tier | Effects |
|---|---|---|
| **Famine** | MUST | Production falls or consumption exceeds supply; hunger spreads; morale declines |
| **Disease Outbreak** | MUST | Survivors fall ill; medicine is consumed; fear and distrust rise |
| Severe storm | COULD | Damage, losses, displacement |
| External threat (raid) | COULD | Security concerns and tension rise |

Each crisis has a trigger, start event, active period, effects, resolution and narrative consequences. `Crisis` uses Template Method (`advance` is final; `applyEffects` is abstract). Adding a storm later should need **no** change to the engine. That is the OCP demonstration.

### 6.2 Resources

Food, water, medicine. Food(t+1) = Food(t) + Production − Consumption − Losses. Quantity never goes negative. Each `Resource` owns and protects its own invariant (see section 12 for how that works with parallel workers).

### 6.3 Chapters [CHANGED: four, threshold-driven]

**MUST has four chapters.** The original's chapter III (Collapse) is folded into the build-up to chapter IV, and the original's chapter V becomes an extended epilogue (SHOULD).

| Chapter | Purpose | Enter when (any listed condition set is met) |
|---|---|---|
| **I. A New Beginning** | Rebuilding, cooperation, the Observer looks helpful | Start of run |
| **II. The Fracture** | Shortages and unreliable information damage trust | Average trust below **T₁** *or* a shortage (food or medicine) is active for **N₁** ticks *or* first Observer intervention with a visible effect |
| **III. The Revelation** | The user finds altered reports and hidden records; collapse accelerates | The user has discovered at least **E** pieces of Observer evidence *or* Observer exposure level crosses **X** *or* average morale below **M₁** with trust below **T₂** |
| **IV. The Last Recording** | The settlement fractures beyond repair and falls silent; the Observer completes its experiment | Active population (alive and present) below **P** *or* morale below **M₂** and trust below **T₃** for **N₂** ticks |
| *(SHOULD)* V. Epilogue | Extended final recording and recap | Immediately after IV resolves |

All thresholds (T, E, X, M, P, N) are values in config, tuned using the seeded run.

**Guaranteeing the broad arc without a timer** **[NEW]**. Transitions are decided by simulation state, never by a clock. Three guard rails keep the story from stalling or skipping:

1. **Minimum dwell.** A chapter lasts at least **D_min** simulated days. This stops a bad-luck cascade from rushing the story.
2. **Pressure, not force.** If a chapter is overdue (past **D_soft**), the `HazardScheduler` and Observer policies raise pressure through normal simulation means: a famine starts, a policy fires earlier, a hidden record gets "leaked" into the user's feed. Stats move, and the transition fires on its own rules.
3. **Hard backstop.** If a chapter is still open at **D_hard**, the coordinator forces the transition and records it as a `ChapterForced` event, visible in the metrics panel. This should essentially never fire in a tuned run, and the test suite asserts that 20 seeded runs never reach it.

Implementation: a `ChapterPolicy` (Strategy) per chapter evaluates a read-only `StoryState` each tick boundary. The Narrator announces the transition and can cite which condition triggered it. Chapter changes are persisted.

**User decisions must matter.** Decisions change trust, resources and who survives, so thresholds are reached by different paths. The broad tragic direction stays; the route and the people involved vary.

### 6.4 Tragic ending and sensitive themes [CHANGED]

The original allowed the story to address death, despair and suicide. In this revision the heaviest events are **fully implied and non-graphic, and never named.** The Narrator and recap use language such as *"the settlement fell silent"*, *"the east shelter was empty by morning"*, *"her chair stayed turned toward the window"*. Rules:

- Templates for chapters III and IV are written in this register from the start; no explicit variants exist to select by accident.
- Narrator test: a keyword test over all templates fails the build if a banned term appears.
- The ending focuses on relationships, loss, responsibility and what the community carries, as the original already asks.
- Final recording keeps the Observer's closing line. Human voices stop, the Observer remains active.

## 7. Event-driven storytelling engine

Unchanged. Simulation generates events, the Narrator interprets them, the user experiences the story. Events are immutable, carry an id, tick, type, survivor ids, location, severity, data and source references.

**Narrator:** picks events worth attention, groups related ones, selects templates deterministically (seeded), uses memories and relationships for context, keeps a short history to avoid repetition, can trigger a `ChoiceMoment`, and links each caption to its source events. It never invents simulation facts. No LLM in MUST.

**Prioritisation:** Minor (background), Significant (short update), Critical (full scene or decision).

**Templates:** write at least 40 authored variants early, in the restrained register of 6.4. Example: *"Day {day}. {survivor} found that {event}."*

**Fan-out [CHANGED, from the original's concurrency section].** `EventBus` fans out to independent subscribers, each with its own queue. Narrator, Recorder, ObserverAI and Broadcaster never compete for the same message.

## 8. User role, interaction and audience vote

The user is the Humanity Overseer: they observe, inspect characters, read scenes, review Observer recommendations, make critical decisions and investigate suspicious records. Screens: **Opening, Story, People, Recovered Records, Final Recording.** The settlement map is optional (SHOULD) and not on screen by default.

**Decision flow** (kept): Narrator detects a critical moment, `ChoiceCoordinator` creates a `ChoiceMoment` with options and a default, the simulation pauses at a safe tick boundary, a choice is validated and recorded, the outcome is queued as a command, applied at the next boundary, events are narrated, the simulation resumes.

### 8.1 Audience vote [NEW, SHOULD]

Cheap participation that needs no factions, accounts or trading.

- **Join:** the operator screen shows a short **join code** and a QR code. Phones open `/vote.html`, enter the code, and see the current choice. No login, no Spring Security.
- **Vote:** each phone sends one vote per `ChoiceMoment` over STOMP (`/app/vote`). A session token (stored in the browser) limits it to one vote, and changing your mind before the deadline replaces your vote.
- **Tally:** `ChoiceCoordinator` aggregates votes. When the deadline passes (or the operator closes the vote), it applies the **majority option**. A tie goes to the **option with the smaller worst-case impact on trust**, declared in the choice definition so it is deterministic. With zero votes, the default option applies.
- **Operator override:** the operator can close the vote and pick an option manually. Both paths submit the same `Command`, so the rest of the system does not know the difference.
- **Display:** the Story screen shows the live count in the same quiet style (text counts, no flashing). Phones use the Quiet Cinematic palette.
- **Determinism:** the final outcome of each vote is stored in the decision log with its tick. A repeat run can replay the stored outcomes (section 20), so the audience adds variety without breaking repeatability.
- **Failure mode:** if Wi-Fi fails, the operator screen alone still runs everything. Voting is an addition, never a dependency.

Deliberately out of scope: factions, per-phone commands, trading, scoring.

**Meaningful agency** (kept): decisions affect characters, relationships, resources, future events and the recap. The interface does not promise control the simulation ignores.

## 12. Multithreading and deterministic parallelism [CHANGED, main addition]

Fixed pool of **four region workers**, not a thread per survivor.

| Thread / pool | Count | Responsibility |
|---|---|---|
| `WorldClock` | 1 | Advances virtual time, requests ticks |
| `RegionWorker` pool | 4 | Evaluate survivors of one region, return a `RegionResult` |
| `HazardScheduler` | 1 | Schedules crises |
| `Narrator` | 1 | Consumes events, writes story |
| `ObserverAI` processor | 1 | Analyses state, proposes interventions |
| `Broadcaster` | 1 | Pushes updates to clients |
| `AsyncRecorder` writer | 1 | **[NEW]** Batches events to persistence |
| Spring request threads | Spring | HTTP and WebSocket input |

### 12.1 The determinism contract [NEW]

Four rules make parallel execution produce the same result every run.

1. **Workers own their region, and only read the rest.** Each worker receives the immutable `WorldView` of tick *t* and the survivors it owns. It never writes to another region's survivors or to any shared object. Its only output is a `RegionResult`: events, proposed deltas for its own survivors, **resource claims**, and **migration requests**.
2. **The coordinator merges in a fixed order.** After all workers finish, `TickCoordinator` sorts and applies results by **region id, then survivor id**, then by the action's sequence number inside that survivor. Thread completion order is irrelevant. This is the only place state changes.
3. **Seeded RNG per region and tick.** Each worker builds its generator as `new SplittableRandom(hash(runSeed, regionId, tick))`. No RNG state is carried between ticks or shared between threads, so migrations, worker speed and scheduling cannot shift random draws. `ThreadLocalRandom` and `Math.random()` are banned in the simulation core (an architecture test checks this).
4. **Deterministic event ids.** Workers tag events locally as `(tick, regionId, localSeq)`. The coordinator assigns the global sequence number during the ordered merge. The Narrator and the recorder consume events in that order.

### 12.2 Tick protocol

1. `TickCoordinator` applies queued commands (user decisions, approved interventions, vote outcomes), then builds the immutable `WorldView`.
2. It submits four `RegionTask`s to the pool.
3. It waits for all with `CompletableFuture.allOf()` (or `invokeAll`). A worker failure fails the tick loudly instead of being swallowed.
4. **Ordered merge** (12.1 rule 2): apply deltas, resolve resource claims, apply migrations, then collect events.
5. Publish events to the `EventBus` (fan-out to independent queues).
6. Build and publish an immutable snapshot.
7. Evaluate chapter transitions and pause requests at this boundary.
8. Next tick.

### 12.3 Shared resources and fairness under scarcity

Workers never touch the shared `Resource` during a tick. A hungry survivor produces a `ResourceClaim(regionId, survivorId, amount)`. At the merge, the coordinator walks claims in region-id, survivor-id order and calls `Resource.consume(amount)`. When food runs short, the same survivors go hungry on every run with the same seed, and the Narrator can say who.

`Resource` still enforces its own invariant with a `ReentrantLock` (quantity never below zero). That keeps the invariant safe if another thread touches it, and it is what the **race-condition test** exercises directly: many threads hammering one `Resource` while the quantity must remain valid.

### 12.4 Cross-region handoff

A survivor owned by region A may want to go to region B (for example to the medical zone).

1. During tick *t*, A's worker returns a `MigrationRequest(survivorId, fromRegion, toRegion)`. The survivor is still owned by A and not touched by B.
2. At the merge, the coordinator applies migrations in **(fromRegion, survivorId)** order. It removes the survivor from A's roster and adds it to B's. If B is at capacity, the request is rejected deterministically (lowest survivor ids admitted first) and a `MigrationDenied` event is emitted.
3. The survivor is processed by **B starting at tick *t+1***. It is never processed by two workers in the same tick, and never skipped.

Test: a migration-heavy scenario asserts that every survivor appears in exactly one region roster at every tick boundary.

### 12.5 Pause, resume and commands

RUNNING → PAUSE_REQUESTED → current tick completes → PAUSED → decision submitted and queued → resume → RUNNING. The Narrator requests the pause; the coordinator performs it only after the current tick has been merged. All outside input (REST, STOMP, vote outcomes) is enqueued and applied at the start of the next tick, in arrival order stamped with the tick it applies to.

### 12.6 Metrics

Tick rate, active workers, queue depths, events per second, average tick duration, caption backlog, **recorder queue depth and dropped-minor-event count [NEW]**, and a counter of forced chapter transitions. Metrics are read-only.

### 13.2 Asynchronous recording so persistence never blocks a tick [NEW]

`AsyncEventRecorder` is a decorator implementing `EventRecorder`. The tick thread calls `record(...)`, which does a non-blocking `offer` on a queue and returns immediately. One writer thread drains the queue and writes in batches.

- **Critical events** (decisions, interventions, chapter transitions, evidence) go to a **lossless** queue so the final recap is always correct.
- **Minor events** go to a bounded queue; on overflow they are dropped and counted, never blocking.
- If the database is slow or down, the writer retries with backoff and the metrics panel shows the growing queue. At a configured limit it **switches to the in-memory adapter** and logs that it did.
- On shutdown, the writer flushes the lossless queue before the shutdown test checks for leaked threads.
- Test: a recorder that sleeps 500 ms per write must not change average tick duration beyond a small margin.

Persist events, significant character changes, decisions, interventions, chapter changes, periodic checkpoints and final state. Never write every survivor update every tick.

## 17. Testing strategy [CHANGED]

Categories (unit, integration, concurrency, determinism, narrative) are as before. Concurrency evidence required:

1. **Race-condition test:** many threads consume one `Resource`; final quantity valid.
2. **Determinism test:** same seed and decision log, run twice (and with a deliberately jittered worker speed), gives an identical ordered event log and final state hash. **[NEW]** The jitter run proves that thread timing does not matter.
3. **Shutdown test:** all executors, including the recorder writer, stop with no leaked threads.
4. **Region ownership test:** no survivor is ever in two rosters, or mutated by a foreign worker.
5. **Concurrent command test:** many queued requests apply in a defined order.
6. **Pause/resume test:** pause happens only at a tick boundary.
7. **[NEW] Chapter-arc test:** across 20 seeds, every run passes through all MUST chapters in order and none uses the hard backstop.
8. **[NEW] Persistence contract test:** in-memory and JPA adapters behave the same; slow-recorder test from 13.2.
9. **[NEW, SHOULD] Vote test:** one vote per session, tie-break, zero-vote default, late vote ignored.

**Unsafe race demonstration** (kept): the intentionally unsafe implementation lives as a separate demo class or script, not as a failing test in the normal suite.

**Narrative integrity** (kept): captions cite source events; deceased survivors are not narrated as active; memories reference valid survivors and events; decisions produce recorded commands and consequences; Observer claims are distinguishable from facts; recap is derived from stored history. **[NEW]** plus a banned-term check over all templates (6.4).
